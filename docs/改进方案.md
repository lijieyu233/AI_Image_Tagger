# AI Image Tagger 改进方案

> 基于 2026-08-29 对运行中实例（97 张图、18/18 冒烟用例）的实测诊断。
> 结论先行：**软件不是"坏了"，而是打标质量崩坏 + 零可观测性，让核心功能形同虚设。**

---

## 一、现状诊断

### 1.1 核心问题：CLIP 打标在"乱标"和"不标"之间震荡（P0）

实测数据（本机数据库 123 条 clip 标签）：

| 指标 | 数值 |
|---|---|
| clip 置信度范围 | 0.2205 ~ 0.2869 |
| clip 置信度均值 | 0.2376 |
| 阈值历史 | 0.22（初版）→ 0.25（现值） |

- 阈值 0.22 时代：photo 14 一张图被打上 **约 10 个不相关标签**（凭证、笔记、身份证、车、文件、屏幕、开会、运动、考试、教室…），全是 0.22~0.25 的噪声分。
- 阈值调到 0.25 后：实测单张重分类（photo 47）**top 分数仅 0.236，tagged: 0**；当前 97 张图中 82 张未分类。
- 根因：`scorePhoto()`（backend/src/clip.js:83）用**单一全局固定阈值**做决策，而该流水线的 cosine 分数天然挤在 0.20~0.29 的窄带里，判别裕度 <0.03。任何全局阈值都同时产生大量误标和大量漏标；用户唯一能做的"调阈值"只能在两个失败模式之间摇摆。

当前决策逻辑的其他放大因素：
- 每组取 top 3（`groupScores.slice(0, 3)`），场景/活动等多个 auto 组叠加后，一张图最多可打 10+ 个标签，噪声被组间叠加放大；
- 无 top-k 总量上限、无 margin（top1−top2）判据、无"低置信进待审"的中间态——低于阈值直接丢弃，用户完全看不到分数。

### 1.2 可观测性为零，问题无法自诊（P0）

- `POST /v1/photos/:id/classify` 返回 `{ok:true, tagged:0}`，不带任何分数信息；后端也无日志。
- 批量打标 job 完成后只有 `done` 状态，不输出分数分布、各标签命中数等统计。
- 结果就是：界面显示"打标完成，处理 N 张"，实际 0 个标签，用户无从知道为什么。

### 1.3 工程与体验问题（P1）

1. **`npm test` 实际跑不起来**：`"test": "node --test backend/test/"` 在 Windows + Node 24 下报 `MODULE_NOT_FOUND`（目录参数带斜杠不被识别）。直接 `node --test backend/test/smoke.test.js` 是 **18/18 全绿**的——回归保护网存在但因脚本写法失效。
2. `web/src/api.js` 中 `saveSettings` **重复定义两次**（第 40、45 行），且 `settings`/`getSettings` 两个名字指同一接口，易出隐性 bug。
3. **Electron 桌面壳在本会话无法启动**（`electron.exe` 静默退出，exit 127，`--version` 亦然）。exe 文件本身完好（合法 PE、188MB），判断为当前代理会话沙箱限制 GUI 进程，**需在用户正常终端验证**；但 main.cjs 缺少"后端启动失败/端口被占"的显式报错，出问题时表现为窗口静默不出现。
4. `App.vue` 已膨胀到 **868 行**（本次未提交改动 +641 行），继续叠加功能会失控。
5. 冒烟测试未覆盖打标决策层：阈值/margin/top-k 纯逻辑目前无单测，改参数无保护。
6. 小问题：`buildFilter` 里 review 分支把阈值数字直接内插进 SQL 字符串（当前安全但脆弱）；photo_tags 无 `(photo_id, tag_id)` 唯一约束（依赖 upsert 逻辑正确性）。

## 二、改进方案

### P0：让打标恢复可用（预计 1~2 天）

**1. 重构打标决策策略（clip.js）——放弃单一全局阈值**

- 每图标签总数上限（建议 ≤4），每组 ≤2；
- 引入 margin 判据：top1 − top2 ≥ Δ（如 0.015）才收，或对全组分数做 softmax，收相对概率高者；
- **分数校准**：批量跑完全库后，按各标签分数分布自动推荐每组阈值（如取各标签命中分数的 P60 分位数），写入 `config/tags.json` 的 per-group `threshold`，取代手工全局调参；
- 全部低于阈值时不再静默丢弃：top1 距阈值 < 0.03 的归入"待确认"（低置信标 + review 队列），让用户有东西可看、可纠正。

**2. Prompt ensemble（对窄带分数最直接的提升）**

- 每个标签 2~3 句英文模板（"a photo of X" / "a picture of X" / "an image showing X"），文本嵌入取均值后再归一化。改动集中在 `buildTextEmbeddings()`，推理成本几乎不变（38 → ~100 句，文本编码毫秒级）。

**3. 可观测性（后端 + 界面）**

- job 完成时返回/落盘统计：分数分布（min/P50/max）、各标签命中数、0 命中告警；
- 单张 classify 响应带 top-5 分数；Lightbox 增加"调试条"显示模型在想什么，让阈值有可视依据；
- 后端加最小日志（打标开始/结束/异常，含耗时）。

**4. 设置页阈值体验**

- 阈值改为"宽松 / 标准 / 严格"三档映射，旁边实时显示"当前筛选下预计命中 N 张"（后端加 `/v1/score-preview` 或复用 stats）；保存后提示"需重跑打标生效"。

### P1：回归保护与体验修补（预计 2~3 天）

5. **修 `npm test`**：改为 `"test": "node --test"`（Node 24 默认递归发现 `**/*.test.js`），Windows/目录写法问题随之消失；验证 18/18 恢复绿色。
6. **新增决策层单测**：把阈值/margin/top-k/互斥逻辑抽成纯函数，用固定 fake embeddings 断言行为（不依赖模型下载）；另加一条"分数窄带防护"测试（全部分数 0.22~0.29 时必须产出合理标签而非 0 或 10+）。
7. `api.js` 清理：删除重复的 `saveSettings`/`settings`，统一命名。
8. **App.vue 拆分**：按视图拆 `views/Home.vue、Settings.vue、Vocab.vue、Progress.vue`，共享状态收敛到一个 composable（`useLibrary.js`）。
9. **Electron 壳健壮化**：main.cjs 启动后端失败/端口占用时弹窗报错而非静默；`npm run electron` 前置检查 `web/dist` 是否存在（当前缺失时白屏）。
10. db.js：`photo_tags` 加 `UNIQUE(photo_id, tag_id)` 迁移；review 过滤的阈值改为参数绑定。

### P2：长期项（按需排期）

11. **模型升级评估**：Xenova/clip-vit-base-patch16 或 SigLIP（onnx 社区版），判别力显著更强，直接缓解窄带问题；接口已隔离在 clip.js，替换成本低。
12. **反馈闭环加强**：现驳回仅 +0.008/次（上限 +0.08），太弱；改为 per-tag 动态阈值（驳回即抬至该图分数之上），让"删错标"真正训练系统。
13. 重复检测 hamming 全表 O(n) 扫描 → 1 万张以上时改分桶/BK-tree。
14. `/v1/files` 原图改为流式响应，避免大图读入内存。

## 三、验收标准

1. 在现有 97 张图上重跑打标：每图 1~4 个标签（不再出现 0 或 10+ 两个极端）；人工抽查 20 张，准确率 ≥70%。
2. 阈值三档切换后，`stats.unclassified` 不再出现全有/全无；设置页能看到预计命中数。
3. `npm test` 全绿，含新增决策层用例（窄带分数防护）。
4. Lightbox 能看到每张图的 top-5 分数条；job 完成通知含命中统计。
5. 用户终端 `npm run electron` 可正常拉起窗口（此条只能由用户验证）。

## 四、建议实施顺序

1. P0-1 + P0-2（决策策略 + prompt ensemble）→ 立即重跑全库打标验证手感；
2. P0-3（可观测性）与 P1-5/P1-6（测试）并行；
3. 其余 P1 → P2 按需。
